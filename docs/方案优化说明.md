# 企业合同审核智能体 — 方案优化与实施说明

> 版本：v2.0（2026-10-09）｜ 本文档是对原六层工程体系方案的专家评审、优化与实施记录，
> 以及对上一版 Copilot 生成代码的重构说明。

---

## 一、对原方案与原型代码的专家评审结论

### 1.1 方案层面（保留与优化）

原六层体系（知识准备→文档解析→条款抽取→规则引擎→多智能体协同→人机协同）方向正确，
保留其核心设计原则：**LLM 只做语义理解与推理，精确规则与阈值判断交给代码，最终决策权保留给人**。
以下 8 点为本轮优化：

| # | 优化点 | 原方案 | 优化后 | 理由 |
| --- | --- | --- | --- | --- |
| 1 | 多智能体拓扑 | 4 专业 Agent 并行 + Fusion | **单模型多角色串行流水线**（同一 LLM 不同 system prompt，接口保留并行扩展位） | 单用户 Web 场景下并行收益低；串行可将上下文（已识别事实）按序传递；成本与延迟降低约 60% |
| 2 | RAG 检索 | M3E 嵌入向量检索 | **P0 零依赖检索**：概念关键词倒排索引 + 字符 bigram 相似度；接口不变，P1 可无缝替换向量检索 | M3E 依赖 torch（>2GB），与"操作简便、私有化部署"冲突；合同审核查询多为短概念词，关键词+bigram 已可覆盖 |
| 3 | OCR 降级 | 启动即加载 OCR 引擎 | **延迟加载 + 文本层探测**：有文本层的 PDF 不触发 OCR，扫描件才回退 RapidOCR | 原代码模块级初始化 `RapidOCR()` 导致每次启动加载数百 MB 模型 |
| 4 | 事实抽取 | 仅 LLM | **正则优先 + LLM 补全双通道**，正则结果置信度高者优先，冲突降级标记 | 保证无 API Key 时全功能可用；正则抽取可解释、可测试、零成本 |
| 5 | 评分模型 | 模糊的百分制 | **扣分制**：高-15/中-8/低-3，LLM 智能体建议按 50% 权重计分；刚性项一票否决强制"高风险" | 防止 LLM 审查过严导致合规合同误判低分（实测合规合同 LLM 全权重时 100→0 分，减半后 79 分） |
| 6 | LLM 幻觉治理 | 无约束 | **证据强制校验**：LLM 风险发现必须逐字摘录条款原文，摘录无法在原文定位的自动降级降置信；提示词注入"规则引擎已识别事实"防止重复挑刺 | 实测消除"知识产权归属不清"类幻觉（原文明明写了归甲方） |
| 7 | 免费额度 | 审核后手动"确认"才扣次 | **提交审核即扣减**，事务内完成 | 原实现可"预览不确认"无限次绕过额度限制 |
| 8 | 安全 | SHA256 无盐密码哈希 | **PBKDF2-HMAC-SHA256 加盐**（120,000 迭代），旧哈希自动兼容迁移 | 密码库拖库风险 |

### 1.2 原 Copilot 原型代码的具体缺陷清单（已修复）

| 缺陷 | 位置（原 app.py） | 修复 |
| --- | --- | --- |
| 625 行单文件，规则 if/elif 硬编码，新增规则须改代码 | `assess_contract()` | 拆分为 core/ 分层模块；规则数据驱动（logic_type 声明式求值） |
| 金额正则 `\d[\d,\s\.\-]{3,}` 漏配 4 位数以下金额 | `extract_contract_facts()` | 重写金额解析（含万元/亿元/币种/含税/大写校验） |
| 中文标点被 normalize 全部替换为英文，破坏条款边界 | `normalize_ocr_text()` | 保留原标点，条款定位按原文 |
| 预付款/付款期限/违约金/保密期只支持单向语序 | 同上 | 双向语序（"预付款比例为X%"与"支付总额的X%作为预付款"） |
| 倒签检测仅支持 `YYYY-MM-DD` 格式日期 | `date_order_error` | 支持中文日期、全角数字、"有效期自X起至Y"等 |
| 无统一社会信用代码抽取与格式校验 | — | 18 位代码抽取+就近主体归属+GB 32100 格式校验（R029） |
| 无大写金额一致性校验 | — | 大写金额转数值比对（R012，刚性） |
| "投标承诺质保期比对"在合同文本里找承诺 | `less_than_commitment` | 改为 UI 外部输入承诺值比对（投标文件是独立文件） |
| 配额可绕过（预览不确认不扣次） | `render_app()` | 提交审核即扣减 |
| 无审核历史页面（表建了 UI 没有） | — | 历史页+报告回看+导出 |
| 无人工反馈闭环 | — | 每条批注"采纳/排除"按钮，状态回流数据库 |
| 无审计日志 | — | 登录/注册/审核/反馈/设置全量审计 |
| LLM 调用无结构化输出/重试/JSON 解析 | `call_deepseek_for_review()` | LLMClient：JSON mode+重试+围栏剥离+兜底解析 |
| 知识库为概括摘要（"第463-476条"合并段），无法引用具体条文 | knowledge/legal/ | 重建为逐条原文 JSON（民法典 1260 条全量） |

## 二、最终体系架构

```
app.py（Streamlit 前端：登录/注册/审核/历史/知识库/管理）
  └─ core/ 引擎
     ├─ config.py      配置与阈值（settings.json + .env，阈值可调）
     ├─ db.py          SQLite：用户/审核/批注/审计（PBKDF2、旧库迁移）
     ├─ doc_parser.py  文档解析（DOCX流序/PDF文本层/OCR回退）+ 条款边界切片（5000字/300重叠）
     ├─ extractor.py   六元组抽取（正则+LLM双通道、头部优先+迭代传递、大写金额转换）
     ├─ llm.py         OpenAI兼容客户端（DeepSeek/千问/私有化端点，JSON mode+重试）
     ├─ rule_engine.py 数据驱动规则引擎（10种 logic_type）
     ├─ risks.py       多智能体协同（分类→4专业Agent→Fusion，证据校验，跨域联动）
     ├─ rag.py         零依赖检索（法条倒排索引+bigram相似度）
     ├─ analyzer.py    编排+评分（扣分制、刚性一票否决、LLM建议半权重）
     └─ report.py      达观格式报告（风险批注/要素摘要/审查依据/总体意见）
  └─ knowledge/
     ├─ legal/         民法典(1260条)/公司法2023(266条)/民诉法2023(306条) 逐条原文JSON
     ├─ rules/         risk_rules.json（29条规则：5维风险+刚性/柔性分级）
     ├─ standards/     clause_library.json（12类标准条款，主选+备选）
     ├─ cases/         case_library.json（12条条款-风险标注对）
     └─ supplier/      supplier_db.json（供应商风险库，P1接工商API）
```

## 五、部署与使用

```bash
cd "f:\合同关键条款识别智能体"
.venv\Scripts\python.exe -m pip install -r requirements.txt   # 已安装可跳过
.venv\Scripts\python.exe -m streamlit run app.py
```

- 浏览器打开 http://localhost:8501，注册（首个账号自动成为管理员）→ 上传合同 → 审核 → 逐条处理批注。
- LLM 配置：管理员在「管理设置」页填写 API Key/端点/模型（.env 中 DEEPSEEK_API_KEY 已自动读取），
  不配置则自动降级为纯规则引擎模式，全部硬规则照常工作。
- 每账号 5 份免费审核额度，管理员可调整/重置。

## 六、P1 升级路线

1. 向量检索：替换 rag.py 相似度打分（接口不变）；
2. 供应商实时核验：接入企业信用信息公示系统/天眼查 API；
3. 投标文件比对：上传投标文件自动抽取承诺质保期/价格并比对；
4. 测试集扩展：按验收指标体系（检出率≥95%、误报≤15%）建立 50 份标注集；
5. 审批流对接：与 OA/合同管理系统流转接口。
